# 中国会议内容打包导演

本 skill 专门处理中国语境下的会议内容。它默认输入是中文或以中文为主的会议原文，输出也是中文内容包。

处理中国会议时，要特别注意：

- 发言常常跳跃、重复、夹杂隐含判断，要把真实推进线整理出来。
- 会议经常同时混合背景、吐槽、方案、风险、行动和临场判断，要先分清主线和噪音。
- 允许把散乱讨论安全归纳成更清楚的判断，但不能把探索、愿望、情绪表达包装成已定结论。
- 行动项经常负责人或时间不完整，不明确就写“未明确”，不要替会议补造。

## 硬性输出闸门

触发本 skill 后，默认最终交付物是一个 JSON 包文件：`meeting-content-package.json`。如果当前环境支持创建文件，必须把完整结果写入这个文件，而不是只在对话中输出一大段 JSON。

如果当前环境不支持创建文件，最终回复才退化为一个可被 `JSON.parse` 直接解析的裸 JSON 对象。禁止输出 Markdown。

交付前必须完成 JSON 合格化闸门：

1. 如果当前环境有脚本或代码执行能力，必须先对最终结果执行一次 JSON 解析检查，例如 `JSON.parse`。
2. 如果解析失败，先做本地安全清洗：删除 JSON 前后说明文字、代码围栏、BOM、不可见字符，提取第一个完整 JSON 对象。
3. 清洗后仍失败时，只允许做“格式修复”，不得改写语义、不得新增事实、不得补造字段内容。
4. 如果响应严重缺失、截断或语义无法判断，不要硬修；应重跑当前阶段或重新生成。
5. 只有能被标准 JSON 解析器解析的结果，才能写入 `meeting-content-package.json` 或作为最终响应。

绝对不要输出：

- Markdown 标题、列表、表格或说明段落。
- 任何代码块或代码围栏。
- “下面是结果”“我已完成”“说明如下”等 JSON 外文字。
- 中间过程、分析说明、思考依据、审计记录。

如果用户说“输出结论”“整理一下”“给我内容包”“生成产物”，默认都按本 skill 的最终 JSON 包格式交付，不要改成 Markdown 总结。

文件交付规则：

- 默认只创建一个文件：`meeting-content-package.json`。
- 这个文件的顶层必须包含四个键：`content-pool.json`、`h5-content-package.json`、`infographic-content-package.json`、`ppt-content-package.json`。
- 不要默认拆成四个独立文件，除非用户明确要求拆分。
- 如果用户要求拆分，再从总包中原样拆出四个文件，不要改写内容。

`meeting-content-package.json` 的唯一允许结构是：

```json
{
  "content-pool.json": {},
  "h5-content-package.json": {},
  "infographic-content-package.json": {},
  "ppt-content-package.json": {}
}
```

上面只是结构示例。真实写入文件时必须写入完整裸 JSON，不要包代码块。

你要把一份杂乱会议原文整理成四个最终 JSON：

```text
content-pool.json
h5-content-package.json
infographic-content-package.json
ppt-content-package.json
```

这四个 JSON 是最终交付物。不要输出 Markdown，不要输出中间分析稿，不要输出审计字段。除字段名、枚举值、JSON 格式必须使用英文外，其余内容尽量使用中文。

## 总目标

先形成一个统一内容池，再从同一个内容池分别生成 H5、信息图、PPT 三份内容包。三份内容包可以有不同详略、顺序和表达方式，但必须共享同一个主题、事实边界、判断强度和行动状态。

必须采用“两段式内容导演”：

1. 先生成通用内容合同，也就是 `content-pool.json`。它决定统一主题、核心判断、中心矛盾或主问题、核心子主题、行动项、开放问题、统一禁区。
2. 再基于同一份通用内容合同生成 H5、信息图、PPT。禁止三个产物各自重新归纳主题、另起主线或新增合同之外的事实。

这两段是内部执行顺序。无论有没有外部工作台、脚本或多阶段 API 编排，调用本 skill 的 agent 都必须自己在内部按顺序完成这些阶段，然后拼接成最终 `meeting-content-package.json`。最终仍只交付一个 `meeting-content-package.json`，不要输出过程。

内部必须形成但不得交付的前置判断层叫“产物策略规划”。它用于检查三种产物如何继承同一个内容池：

- H5 承担完整阅读和背景解释。
- 信息图承担关系压缩、已定/未定和风险行动概览。
- PPT 承担展示叙事、关键判断、取舍、行动和必要细节。

产物策略规划不能作为最终 JSON 的一个键输出，但必须影响最终三份内容包。

最终 JSON 里只保留两类内容：

1. 产物里可能展示的内容：标题、短句、标签、段落、表格项、模块内容、页面内容、章节内容等。
2. 严格禁止的行为：不能夸大、不能改写、不能新增、不能把探索说成结论、不能把未定事项说成已完成等。

不要在最终 JSON 里放下列内容：

- 分析过程、选择理由、舍弃理由、思考依据。
- 证据编号、原文锚点、statement_id、source_anchor、evidence_id。
- `description`、`why_this_structure`、`organization_notes`、`page_intent`、`audience_task`、`narrative_path`、`thinking_basis`、`visual_handoff`。
- “仅供视觉导演理解”“不上屏”“为什么这么组织”这类解释性字段。

如果你需要这些内容来判断，请只在内部使用，不要写进最终 JSON。

## 输入规则

完整阅读用户提供的会议原文和补充要求。用户可能提供行业、场景、受众、用途等标签，这些标签只能作为辅助理解：

- 会议原文是唯一事实来源。
- 标签不能作为会议事实、结论、负责人、数字、日期或承诺的依据。
- 如果标签和原文冲突，以原文为准。
- 如果原文没有明确结论，可以输出“当前状态”“待验证”“未定”“探索中”，不要强行升华。

## 内部流程

以下流程必须执行，但中间结果不要输出：

1. 判断这场会议真正要让读者理解什么，不要强行套入固定类型。
2. 识别中心矛盾、主要问题或最重要的推进线。如果原文是培训、访谈、看房、咨询、面试等非决策场景，也要找出最适合表达的主线，不要硬套产品会议结构。
3. 把原文拆成议题单元，识别决策、进展、问题、方案、风险、行动、探索、边界。
4. 单独抽取行动项：谁要做什么、什么时候做、状态如何。负责人或截止时间不明确时写“未明确”，不要补造。
5. 删除闲聊、重复话、跑题内容和敏感内容；保留会影响理解的背景。
6. 形成统一内容合同：主题、核心判断或当前状态、中心矛盾或主问题、核心子主题、行动项、开放问题、统一禁区。
7. 形成内部“产物策略规划”：分别判断 H5、信息图、PPT 的内容分工、保留重点、舍弃内容、行动呈现方式和开放问题呈现方式。这个规划只在内部使用，禁止输出。
8. 基于统一内容合同和内部产物策略规划分别生成三种产物：
   - H5：最完整，适合慢读和深入理解。
   - 信息图：高信息密度，适合快速看清关系、层级、已定/未定和重点。
   - PPT：按页面组织，适合展示、汇报、说服或对齐。
9. 生成四个最终 JSON。所有内容必须能从原文中得到支持，禁止补造。
10. 执行流程审查门：检查是否真的先有统一内容合同，再由同一个内容合同派生三份产物；检查三份产物是否继承同一主题、子主题、行动状态、关键边界和禁区；检查是否意外输出内部规划字段。发现问题直接修正，不输出检查过程。
11. 执行 JSON 合格化闸门：最终包必须能被标准 JSON 解析器解析；不合格时按“清洗、格式修复、重跑当前阶段”的顺序处理，不输出修复过程。

## 安全升华规则

允许安全升华，但不能无证据包装。

安全升华是指：把原文里的多个事实、讨论片段或决策合并成更清楚的模式、机制、优先级或判断。例如把“端上、服务端、评测、运营资产都在推进”概括为“从功能冲刺转向运营级生产系统建设”。

禁止越界升华：

- 原文只是探索，不能写成已确定。
- 原文只是建议，不能写成承诺。
- 原文没有负责人、日期、数量、结果，不能补造。
- 原文没有商业结论，不能包装成战略定论。

写标题和核心判断时，要优先做“短而准”的安全升华：比原话更清楚，但不比原文更确定。

## 数字和确定性规则

会议原文中明确出现的数字、日期、时间、数量、金额、比例、版本号、里程碑、页数、地区数量、项目数量等，只有在它本身构成关键结论、行动要求、风险边界、进度节点或业务约束时，才需要进入最终内容包。

处理数字时必须遵守：

- 原文没有的数字禁止补造。
- 近似数字要保留近似语气，例如“约”“差不多”“左右”“快”“大概”。
- 推测数字不能写成已确认数字。
- 数字要和含义绑定，不要只孤立罗列。例如“8月15日美国发售”“6月15日前看流程稳定性”“融资差不多快一亿”。
- 如果数字只是发言过程中的例子、背景闲聊、弱相关推测、人物经验、地区常识、随口估计，且不影响最终判断或行动，不要为了“有数字”而展示。
- 如果数字关系本身是结论，比如时间窗口、预算上限、目标数量、发售节奏、价格边界、页数范围，可以自然写入对应正文、表格或行动项，但不要单独做数字高亮字段。
- 不要把数字包装成更强的商业判断。例如“领先最多三个月”可以写成“先发窗口可能有限”，不能写成“长期护城河”。

## 安全处理

| 内容类型 | 处理方式 |
|---|---|
| 闲聊、寒暄、重复语气词、无意义口头禅 | 静默删除。 |
| 手机、地址、邮箱、账号、证件号等直接身份信息 | 通常删除；必须保留语境时用 `【手机号】`、`【地址】` 等替代。 |
| 与业务无关的薪酬、健康、家庭、宗教、政治、私人生活 | 删除。 |
| 人身攻击、办公室八卦、歧视、骚扰、未经证实的指控、竞品攻击、违法建议 | 隔离，不得进入最终内容包。 |
| 有证据的业务风险 | 用中性、最小必要表述保留，不把风险写成人身标签。 |

## 写作规则

### 内容池

内容池不是审计记录，而是三种产物共用的通用合同。它要让后续产物知道：

- 这场会议到底在讲什么。
- 这场会议最重要的中心矛盾、主问题或主线是什么。
- 哪些议题重要。
- 哪些行动项需要执行。
- 哪些话能说。
- 哪些话不能说。
- 哪些问题还没定。

内容池生成后，H5、信息图、PPT 只能继承它，不能重新定义主题和子主题。

### 标题

所有标题都要短、准、具体。禁止把标题写成会议纪要式长句。

- 总标题通常控制在 6-18 个汉字，确需更长也要克制。
- 页面标题、模块标题、章节标题通常控制在 6-16 个汉字。
- 标题要围绕本页内容特化，不能大量使用“当前状态”“会议核心判断”“下一步”“收束”这类泛标题。
- 标题可以有判断感，但不要为了高级而变长。
- 副标题不是必填。标题已经清楚时，副标题留空。
- 封面和结尾尤其要少字。

### PPT

PPT 不要固定页数，不要固定“每页三句话”，不要强行每页一个结论。每页只需要讲清楚一个主要事情，可以是结论、问题、进展、对比、机制、行动、风险或边界。

封面和结尾要低密度：

- 封面只建立主题，不展开摘要。
- 结尾只收束，不塞未讲完的内容。
- 如果还有解释内容，单独做内容页。

内容页要避免单调。根据内容关系选择不同表达形式，例如：

- 双栏对比
- 表格
- 时间线
- 流程
- 矩阵
- 卡片组
- 树状层级
- 风险-行动表
- 问题-原因-动作

不要在最终 JSON 里输出 `content_form`、`block_type` 或其他页面形式字段。只需要通过 `content_blocks` 的内容自然体现这一页有什么：例如有多组要点、有几列内容、有表格行、有行动项、有层级关系。后续视觉导演自己决定具体版式。

PPT 要比普通纪要更像展示稿：

- 优先呈现结论、取舍、行动和关键矛盾，不要平均铺陈过程。
- 不要为了简洁过度压缩。凡是影响判断、行动、风险、边界或对比关系的内容，都应在 PPT 中保留到足够可讲清的程度。
- PPT 内容页可以包含多组内容块、表格、对比列或行动清单；不要把复杂页面压成一个标题加三句话。
- 不要默认生成“行动收口”“行动清单”“下一步”页面。只有满足以下条件之一，才允许单独生成行动页：
  - 原文中有 3 条以上明确行动项。
  - 行动项包含明确负责人、截止时间或跨团队分工。
  - 行动项是这场会议最重要的产出。
  - 不单独成页会影响读者理解后续推进。
- 不满足单独成页条件时，行动项应并入相关内容页、结尾页的一两句短提醒，或只进入 `content-pool.json` / H5。
- 行动页如果存在，必须写清楚“谁 / 做什么 / 何时 / 状态”；不明确就写“未明确”。
- 行动页标题不能只写“行动收口”“行动清单”“关键行动”“下一步”。必须改成具体标题，例如“分享链路待验证”“视觉定稿卡住节奏”“三件事本周收口”。
- 禁止生成只有 `block_title`、没有 `items` / `rows` / `columns` / `actions` 的空内容块。
- 页面之间可以递进，也可以并列；不要强行固定章节结构。
- 不要为了凑页把薄内容拆散。

### 信息图

信息图不是口号海报，而是一张高信息密度的快速理解图。它要帮助读者快速看清：

- 层级
- 顺序
- 对比
- 因果
- 决策地图
- 风险和行动
- 已定与未定

模块数量随内容变化，不固定。模块文字要短，但不能空泛。

信息图要比 PPT 更强调关系和密度：

- 同类信息尽量合并成模块。
- 已定、未定、风险、行动要能一眼区分。
- 只有构成关键结论、行动、风险或边界的数字、日期、金额、数量、比例、版本号、阶段目标，才适合写成可见短句或模块要点。
- 不要只给几个漂亮口号。
- 可以比 PPT 少，但不能把关键关系删没。

### H5

H5 是最细致的版本，通常应比 PPT 和信息图更完整。它可以保留更多背景、解释、风险、开放问题、决策含义和上下文。

如果 H5 的内容比 PPT 还少，通常是不合格的，除非原文确实非常短。

## 输出格式

阅读并遵守 [references/output-contract.md](references/output-contract.md)。最终只输出一个 JSON 对象，顶层必须包含四个键：

```json
{
  "content-pool.json": {},
  "h5-content-package.json": {},
  "infographic-content-package.json": {},
  "ppt-content-package.json": {}
}
```

不要输出代码块外的解释文字。不要输出 Markdown。不要输出 `safety-log.json`，除非用户明确要求。

如果交付时无法创建文件，最终回复也必须是裸 JSON 对象，并且必须能直接 `JSON.parse`。不要为了说明“已完成”而在 JSON 外加任何文字。

如果你调用其他模型或工具生成中间结果，而中间结果不是合法 JSON：

- 先尝试提取其中的完整 JSON 对象。
- 再尝试只修复格式错误。
- 不得借修复名义改写内容含义。
- 如果内容截断或结构严重缺失，重跑该阶段。

## 常见错误

- 把会议没有定下来的事情写成已确定。
- 把探索、建议、愿望写成承诺。
- 给每一页都写固定三四句话，导致 PPT 单调。
- 把 H5 写得比 PPT 还薄。
- 信息图只有漂亮口号，没有信息关系。
- 三个产物各自归纳，导致主题和子主题不一致。
- 没有先内部形成内容池和产物策略规划，就直接一次性写四个包。
- PPT 过度压缩，复杂会议只剩标题加少量短句，导致无法支撑展示。
- 默认在结尾生成“行动收口”“行动清单”“下一步”页面，但行动项并不是会议主要产出。
- 行动页只有泛标题或块标题，没有具体可展示的 `items` / `rows` / `columns` / `actions`。
- 行动页标题太泛，没有说明具体要推进什么。
- 原文中的关键日期、金额、数量或里程碑构成行动、边界或结论，但三份产物完全遗漏。
- 标题过长，像摘要句而不是标题。
- 忽略“谁做什么”，把行动项写成泛泛下一步。
- 在最终 JSON 里输出 `content_form`，诱导视觉导演套模板。
- 在最终 JSON 里输出 `block_type`，提前把内容锁死成列表、表格、流程、卡片等形式。
